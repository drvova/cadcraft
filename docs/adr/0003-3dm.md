# ADR 0003: Rhino `.3dm` interoperability — our own reader, from openNURBS read as documentation

Status: **accepted**, 2026-11-14 (option 1, the owner's decision). First reader and writer landed the same day; see *Outcome*.

## Context

Jewellers who model in Rhino want to bring their pieces into CADCraft and send them back. Rhino's
native file is `.3dm`. CADCraft's rules: file formats come from public specifications and our own
synthetic tests; dependencies are permissive, pure Rust, from crates.io and build for
`wasm32-unknown-unknown`; input files are hostile and never crash the app; no file produced by
Rhino is committed.

## What was found (2026-11-14)

What was read: the openNURBS repository's front page and README, the first lines of its `LICENSE`,
one McNeel forum thread, the RhinoCommon `File3dmTypeCodes` API page title, the PRONOM registry
entry, and crates.io metadata (name, licence, repository, dependency names). **No openNURBS
source file and no crate source was read.**

- **openNURBS** (https://github.com/mcneel/opennurbs, licence at
  https://github.com/mcneel/opennurbs/blob/8.x/LICENSE): C++, "Copyright (c) 1993-2018 Robert
  McNeel & Associates", provided "as is"; a permissive McNeel licence (with bundled zlib). It is
  C++, so it cannot be a dependency (not pure Rust, no wasm32 build without a C++ toolchain).
- **No public specification of the 3dm layout exists.** McNeel staff, asked for a format
  description, answered that "nothing like this exists" and pointed to the header comments and
  source (https://discourse.mcneel.com/t/i-am-looking-for-a-3dm-file-format-description/158947).
  PRONOM (https://www.nationalarchives.gov.uk/PRONOM/fmt/864) likewise says the format is
  defined by the openNURBS toolkit. The RhinoCommon API
  (https://developer.rhino3d.com/api/rhinocommon/rhino.fileio.file3dmtypecodes) lists typecode
  names and the 4-byte typecode bit layout, but not the chunk grammar or object serialisations.
  **The only full description of the format is the openNURBS source code.**
- **Pure-Rust crates** (crates.io, searched `3dm`, `rhino`, `opennurbs`, `rhino3dm`):
  - `cadmpeg-codec-rhino` 0.6.12, Apache-2.0, https://github.com/cadmpeg/cadmpeg, first published
    2026-07-12, 17 versions. Depends on `cadmpeg-core/-ir/-container`, `flate2`, `crc32fast`,
    `roxmltree`, `serde`, `sha1/sha2`, `tempfile`. Licence acceptable; maturity young, provenance
    of its format knowledge unknown (it was very likely written from openNURBS), wasm32 build not
    verified (`tempfile` in normal dependencies is a warning sign), entity coverage not verified.
  - `cadaclysm-sdk` 0.14.2, Apache-2.0: loads native libraries (`libloading`) — not pure Rust in
    effect; rejected.
  - No `rhino3dm`/`opennurbs` Rust crate exists (McNeel's `rhino3dm` is C++/Python/JS-wasm, built
    from openNURBS).

## Options

1. **Our own reader written from the openNURBS source as documentation.** The licence is
   permissive, so learning the layout from it is not the GPL problem; but it is not a "public
   specification" in the sense `CLAUDE.md` uses, so it needs the owner's explicit allowance. If
   allowed: read headers/comments, write a format note in our own words under `docs/`, write the
   reader from the note (no copied code), test on synthetic files from our own writer.
2. **Depend on `cadmpeg-codec-rhino`** after an audit: wasm32 build, hostile-file fuzzing (no
   panics), coverage. Fast if it passes; risk is a young single-vendor crate on our file path.
3. **No 3dm; meet jewellers through formats Rhino already exports** with public specs: STL
   (already written by `STLOUT`), OBJ (public), and DXF for curves (Rhino exports DXF, which we
   read). Zero format risk today; worse experience (no layers/names in STL, an extra export step).

## Decision

**Option 1.** The owner chose CADCraft's own reader, written from the openNURBS source used as
documentation only. Before any source file was read, the licence was checked (below); the
layout was then written down in our own words in [`docs/formats/3dm.md`](../formats/3dm.md),
and the Rust reader and the test writer were written from that note, not from the C++ (no code,
comment or identifier copied beyond the format's own typecode names and class ids).

### The licence gate (2026-11-14)

The complete `LICENSE` file on openNURBS's default branch
(https://github.com/mcneel/opennurbs/blob/8.x/LICENSE, 48 lines) was read in full. In our own
words, it says:

- openNURBS is copyright 1993–2018 Robert McNeel & Associates, "All Rights Reserved"; Rhinoceros
  is McNeel's registered trademark.
- The software is provided as is, with every implied warranty (fitness, merchantability)
  disclaimed.
- The toolkit bundles an unmodified subset of zlib 1.1.3 for mesh and bitmap compression, under
  zlib's own licence, reproduced in the file: use for any purpose, including commercial, altering
  and redistributing allowed, provided the origin is not misrepresented, altered versions are
  marked, and the notice is kept in source distributions. The zlib data format is described by
  RFC 1950–1952.

The source files' headers add "For complete openNURBS copyright information see
http://www.opennurbs.org"; the README presents the toolkit as C++ source that other
developers use to read and write 3dm files (it says more than 400 teams do).

**Finding.** The licence is **not copyleft** (no GPL/LGPL/AGPL-style terms, no share-alike, no
obligation on works that learn from it) and it **does not forbid** studying the source or
writing an independent implementation of the file format. It is terse: beyond the zlib part it
grants no rights in so many words ("All Rights Reserved" with a warranty disclaimer), which is
why nothing of openNURBS is copied, linked or redistributed — only facts about the file layout
(field orders, sizes, typecodes, class ids) were learned, which is what a format note records.
The gate's conditions were met, so the work proceeded.

### What was read in openNURBS (shallow clone of `8.x`, deleted afterwards)

Only the parts that describe the file layout, by searching for the functions that read and
write each structure:

- `LICENSE`, `README.md`.
- `opennurbs_3dm.h` — the typecode table.
- `opennurbs_archive.cpp` — start section, chunk begin/end (short and long chunks, 4/8-byte
  values by archive version, CRC handling), the chunk-version byte, primitives (strings, uuids,
  colours, points, planes, circles, arcs, lines, intervals, arrays), object (class) framing,
  properties, settings, layer and object table records, table end, end mark. Not the rest.
- `opennurbs_zlib.cpp` — compressed buffers (size, CRC, method, inflate chunk).
- `opennurbs_crc.cpp` — two comment lines saying the CRC is zlib's `crc32`.
- `opennurbs_mesh.cpp` — mesh write/read, face array, the compressed vertex arrays, the mapping
  tag.
- `opennurbs_nurbscurve.cpp`, `opennurbs_polylinecurve.cpp`, `opennurbs_linecurve.cpp`,
  `opennurbs_arccurve.cpp`, `opennurbs_polycurve.cpp` — each class's write/read.
- `opennurbs_layer.cpp` — layer write/read (the fields up to the layer id).
- `opennurbs_3dm_attributes.cpp` — object attributes, both layouts (to the name and layer).
- `opennurbs_3dm_properties.cpp` — properties write (the toolkit version chunk).
- `opennurbs_3dm_settings.cpp` — the units-and-tolerances record and the unit codes.
- `opennurbs_extensions.cpp` — the order a model writes its tables in.
- `opennurbs_defines.h` — object type values and length unit codes.
- The `ON_OBJECT_IMPLEMENT` lines of the class files for the class ids (layer, mesh, curves,
  point, NURBS surface, brep, extrusion, SubD).

An attempt to build openNURBS's `example_read` in the scratchpad (to open CADCraft's files with
McNeel's own reader) was not permitted in the session, so that check is still open.

## Scope (as planned)

- First: header, start section, properties, the table/chunk structure (typecodes, long/short
  chunks, CRCs, 32/64-bit lengths by version), layers and object names; **meshes** (to a measured
  report `{triangles, volume, grams by metal, bounds}` through an `import3dm` command, and shown in
  3D once the engine holds imported meshes); **curves** (polylines, lines, arcs, NURBS curves as
  splines on their layers). Compressed (zlib) buffers via a permissive pure-Rust inflater.
- Not soon: **NURBS surfaces and breps.** Needs a NURBS surface evaluator, trimming curves and a
  tessellator to display/measure (a reader for the data alone is smaller); a real kernel (booleans,
  fillets) is far beyond.
- Export: the piece as a 3dm mesh plus its profile/rail curves on named layers.
- Never crash: bounded chunk depth, lengths checked against the remaining buffer, allocation caps,
  a `hostile_3dm_does_not_panic` test.

## Outcome (2026-11-14)

- **Reader** `crates/io/src/rhino3dm/` (L3): archive versions 2–4 (4-byte chunk lengths) and
  50–80 (8-byte; Rhino 5–8); start section and comment, properties (toolkit version), settings
  (model units), layer table (name, colour, index), object table (type, class, attributes: name
  and layer, both attribute layouts), meshes (compressed layout 3.x: faces, single-precision
  vertices, normals), curves (line, arc/circle, polyline, NURBS with rational weights, joined
  curves nested up to 24 deep). Points, NURBS surfaces, breps, extrusions and SubD are recognised
  by class id and counted; every other chunk is skipped by its length. Hostile input: lengths
  checked against what remains, counts and inflated bytes capped (`Limits`), every truncation and
  thousands of mutations tested, plus Hegel properties in the engine.
- **Writer** (same module): archive 50/60/70/80, the same subset, deterministic bytes; used by
  the tests and by `EXPORT3DM`. Checked only by CADCraft's own reader.
- **Commands**: `IMPORT3DM {path|data, curves?, faces?, query?}` (and `IMPORT` of a `.3dm`):
  per-mesh `{name, layer, vertices, faces, triangles, closed, volumeMm3, grams by metal, bounds}`
  in millimetres; curves added as lines, arcs, circles, polylines and splines on the file's
  layers (projected onto XY when off it), usable by `PIECE {profile: {curve}}`; meshes added as
  3DFACE objects only with `faces: true` (the drawing has no mesh object). `EXPORT3DM` writes the
  cast piece (STLOUT's merged solid) on layer Metal with its section (Profile) and finger circle
  (Finger).
- **Interface**: File ▸ Import accepts `.dxf, .dwg, .3dm` and shows the report in the notice.
