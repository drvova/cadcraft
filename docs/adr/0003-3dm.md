# ADR 0003: Rhino `.3dm` interoperability — no reader yet; the owner decides the source of the format

Status: proposed (owner decision needed), 2026-11-14.

## Context

Jewellers who model in Rhino want to bring their pieces into CADCraft and send them back. Rhino's
native file is `.3dm`. CADCraft's rules: file formats come from public specifications and our own
synthetic tests; dependencies are permissive, pure Rust, from crates.io and build for
`wasm32-unknown-unknown`; input files are hostile and never crash the app; no file produced by
Rhino is committed.

## What was found (2026-11-14)

What was read: the openNURBS repository's front page and README, the first lines of its `LICENSE`,
one McNeel forum thread, the RhinoCommon `File3dmTypeCodes` API page title, the PRONOM registry
entry, and crates.io metadata (name, licence, repository, dependency names). **No openNURBS
source file and no crate source was read.**

- **openNURBS** (https://github.com/mcneel/opennurbs, licence at
  https://github.com/mcneel/opennurbs/blob/8.x/LICENSE): C++, "Copyright (c) 1993-2018 Robert
  McNeel & Associates", provided "as is"; a permissive McNeel licence (with bundled zlib). It is
  C++, so it cannot be a dependency (not pure Rust, no wasm32 build without a C++ toolchain).
- **No public specification of the 3dm layout exists.** McNeel staff, asked for a format
  description, answered that "nothing like this exists" and pointed to the header comments and
  source (https://discourse.mcneel.com/t/i-am-looking-for-a-3dm-file-format-description/158947).
  PRONOM (https://www.nationalarchives.gov.uk/PRONOM/fmt/864) likewise says the format is
  defined by the openNURBS toolkit. The RhinoCommon API
  (https://developer.rhino3d.com/api/rhinocommon/rhino.fileio.file3dmtypecodes) lists typecode
  names and the 4-byte typecode bit layout, but not the chunk grammar or object serialisations.
  **The only full description of the format is the openNURBS source code.**
- **Pure-Rust crates** (crates.io, searched `3dm`, `rhino`, `opennurbs`, `rhino3dm`):
  - `cadmpeg-codec-rhino` 0.6.12, Apache-2.0, https://github.com/cadmpeg/cadmpeg, first published
    2026-07-12, 17 versions. Depends on `cadmpeg-core/-ir/-container`, `flate2`, `crc32fast`,
    `roxmltree`, `serde`, `sha1/sha2`, `tempfile`. Licence acceptable; maturity young, provenance
    of its format knowledge unknown (it was very likely written from openNURBS), wasm32 build not
    verified (`tempfile` in normal dependencies is a warning sign), entity coverage not verified.
  - `cadaclysm-sdk` 0.14.2, Apache-2.0: loads native libraries (`libloading`) — not pure Rust in
    effect; rejected.
  - No `rhino3dm`/`opennurbs` Rust crate exists (McNeel's `rhino3dm` is C++/Python/JS-wasm, built
    from openNURBS).

## Options

1. **Our own reader written from the openNURBS source as documentation.** The licence is
   permissive, so learning the layout from it is not the GPL problem; but it is not a "public
   specification" in the sense `CLAUDE.md` uses, so it needs the owner's explicit allowance. If
   allowed: read headers/comments, write a format note in our own words under `docs/`, write the
   reader from the note (no copied code), test on synthetic files from our own writer.
2. **Depend on `cadmpeg-codec-rhino`** after an audit: wasm32 build, hostile-file fuzzing (no
   panics), coverage. Fast if it passes; risk is a young single-vendor crate on our file path.
3. **No 3dm; meet jewellers through formats Rhino already exports** with public specs: STL
   (already written by `STLOUT`), OBJ (public), and DXF for curves (Rhino exports DXF, which we
   read). Zero format risk today; worse experience (no layers/names in STL, an extra export step).

## Decision

**Do not write 3dm code until the owner chooses between options 1 and 2.** The task's condition
for a spike — a clean path from a public description — is not met: no public specification
exists. Meanwhile option 3 is the documented route (Rhino → DXF for curves, Rhino → STL/OBJ for
meshes; CADCraft → STL back). Recommendation: option 1 (we own the reader, it can be bounded and
hostile-tested like the DXF/DWG readers), with option 2 evaluated first as a cheap check.

## Scope once a source is chosen

- First: header, start section, properties, the table/chunk structure (typecodes, long/short
  chunks, CRCs, 32/64-bit lengths by version), layers and object names; **meshes** (to a measured
  report `{triangles, volume, grams by metal, bounds}` through an `import3dm` command, and shown in
  3D once the engine holds imported meshes); **curves** (polylines, lines, arcs, NURBS curves as
  splines on their layers). Compressed (zlib) buffers via a permissive pure-Rust inflater.
- Not soon: **NURBS surfaces and breps.** Needs a NURBS surface evaluator, trimming curves and a
  tessellator to display/measure (a reader for the data alone is smaller); a real kernel (booleans,
  fillets) is far beyond.
- Export: the piece as a 3dm mesh plus its profile/rail curves on named layers.
- Never crash: bounded chunk depth, lengths checked against the remaining buffer, allocation caps,
  a `hostile_3dm_does_not_panic` test.
